# Nokia N1 平台 Miracast (Wi-Fi Display Sink) 解码、渲染管线与适配性能评估报告

## 1. 核心评估结论 (Executive Summary)

针对用户提出的「N1 Box 能否作为鸿蒙 4.2 手机扩展屏幕（电脑模式）」的诉求，从 **视频解复用、MediaCodec 硬件解码、2048x1536 视网膜屏幕适配与延迟预算** 角度，得出以下关键结论：

1. **流水线 100% 可复用**：
   - 现有的 `VideoPlayer` 同步硬解与零拷贝渲染流水线（`MediaCodec` + `SurfaceView` + HWC 硬件叠加层）**完全可以无缝复用**，甚至比 AirPlay 2 更简洁。
2. **解复用极低开销**：
   - Miracast 采用标准 **MPEG2-TS over RTP/UDP** 封装。TS 流解复用属于轻量级字节扫描，直接提取出 PES 中的 H.264 Annex B 码流。在 Intel Atom Z3580 2.33 GHz 四核处理器上，解复用 CPU 占用率 **<0.3%**，无性能瓶颈。
3. **4:3 屏幕适配最佳实践（化黑边为功能）**：
   - 鸿蒙「电脑模式」原生按 16:9 宽屏（1080P）设计。在 Nokia N1 2048x1536 (4:3) 屏幕上，推荐采用 **16:9 等比居中显示（2048x1152）**，上下各预留 192 像素纯黑边。
   - 强烈建议将上下 192 像素黑边打造为 **「副屏拓展控制栏」**（显示实时码率、延迟、状态、虚拟触控板/手势栏），兼顾完美画面比例与操作便利。
4. **端到端延迟预算极佳**：
   - 得益于 Wi-Fi Direct (P2P) 点对点 5GHz 直连（无需路由中转），典型空口延迟仅 2~4ms。
   - 端到端总延迟预计可压至 **24 ~ 32 ms (60fps 时约 1.5 帧)**，鼠标指针与窗口拖拽极为跟手。

## 2. 数据封包形态与 TS 解复用开销对比 (Miracast vs AirPlay 2)

| 维度 | AirPlay 2 镜像 / 扩展屏 | Miracast (Wi-Fi Display) |
| :--- | :--- | :--- |
| **底层传输** | 局域网 TCP (Port 7100) | Wi-Fi Direct P2P RTP over UDP |
| **封装协议** | 自定义 128-byte Header + AVCC Slices | **MPEG2-TS (Transport Stream, 188 字节定长包)** |
| **加解密算法** | AES-128-CBC (FairPlay SAP v2.5 协商) | 可选 HDCP 2.0/2.2（若声明 `none` 则为**纯明文**） |
| **NALU 格式** | 4 字节大端长度 (AVCC)，需原地换 Start Code | **PES 内直接承载 `00 00 00 01` Annex B 码流** |
| **音频格式** | ALAC / PCM / AAC-ELD | AAC-LC / LPCM / AC-3 |

### 2.1 MPEG-TS 解复用实现复杂度与 CPU 消耗
- **数据结构**：每个 TS 包 188 字节，同步字节 `0x47`。
- **解复用流程**：
  ```
  [ RTP / UDP Socket ] (每包 ~1316 字节 = 7 个 TS 包)
           |
           v
  [ TS Demuxer ] (状态机轮询)
     |--> 提取 PAT (PID 0x0000) 与 PMT (PID 0x0100) -> 确定 Video/Audio PID
     |--> 过滤 Video PID (通常 0x1011) -> 聚合 PES 负载
     |--> 解析 PES Header (获取 PTS 90kHz 时间戳)
     +--> 直接得到 H.264 Annex B Slices (带有 00 00 00 01 起始码)
           |
           v
  [ 直接投喂至 VideoPlayer mQueue (new NALPacket(nalData, ptsUs)) ]
  ```
- **Atom Z3580 性能开销测算**：
  - 1080p@60fps 的典型码率为 10 ~ 16 Mbps（约 1.25 ~ 2.0 MB/s）。
  - 每秒需处理 TS 包数量：约 7,000 ~ 11,000 个包。
  - 在 Intel Silvermont 乱序执行架构下，单次 TS 包解析耗时约 30~50 纳秒。
  - **总计算开销**：单核每秒消耗不到 0.5 毫秒 CPU 时间，**总 CPU 负荷 < 0.3%**，几乎不占算力。

## 3. `VideoPlayer` 硬解与渲染流水线复用方案

我们刚在 AirPlay 2 中调通并验证的 `VideoPlayer`（位于 `app/src/main/java/com/n1tools/box/airplay/player/VideoPlayer.java`）具备以下特性：
- 同步非阻塞式轮询：`dequeueInputBuffer(10000)` 与 `dequeueOutputBuffer(bufferInfo, 0)`。
- 低时延队列保护：当堆积超过限额时自动丢弃旧帧。
- 零拷贝直显：`mDecoder.releaseOutputBuffer(outputBufferIndex, true)` 直接将解码帧绑定送显至 `SurfaceView`。

### 3.1 接入契约改造与复用
Miracast 接入该流水线完全零障碍：
1. **输入对接**：
   TS 解复用器每解析出完整的一帧 Video PES，转换为微秒级 PTS：
   $$\text{ptsUs} = \frac{\text{PTS}_{\text{90kHz}} \times 1000000}{90000}$$
   直接构造 `NALPacket` 投递进 `VideoPlayer.addPacker(packet)` 即可。
2. **解码器兼容性验证**：
   - Nokia N1 的 `OMX.Intel.VideoDecoder.AVC` 原生支持 1080p@60fps Baseline / Main / High Profile。
   - 鸿蒙手机在 Miracast 协商中通常输出 H.264 High Profile Level 4.2，完全落在 Intel VED 硬件解码支持范围内。

## 4. 2048x1536 4:3 屏幕适配鸿蒙电脑模式技术方案

### 4.1 鸿蒙电脑模式的画面特性
- 鸿蒙 4.2 手机（如 Mate 60 系列、Pura 70 系列、MatePad 等）在启动无线投屏「电脑模式」时，输出分辨率固定为标准宽屏比例：
  - 默认为 **1080P (1920x1080 @ 60fps / 16:9)**。
  - 部分型号支持协商至 **2K (2560x1440 @ 60fps / 16:9)**。
- 鸿蒙电脑模式的桌面 UI（底部任务栏、右下控制中心、多窗口排列）严格依赖 16:9 视野。如果强行强制 4:3，界面会出现大面积横向压缩或排版错乱。

### 4.2 三种屏幕适配方案对比

```
+-----------------------------------------------------------------------------------+
| 方案 A (推荐默认 - 等比居中 + 黑边功能化):                                            |
|   * 画面尺寸: 2048 x 1152 (16:9 完全保真无变形)                                     |
|   * 上下黑边: 各留 192 像素 (1536 - 1152 = 384 / 2 = 192px)                        |
|   * 视觉体验: 画面居中，字迹极度锐利，窗口比例 100% 还原；                         |
|   * 创新拓展: 顶部 192px 显示 N1 状态栏（Wi-Fi/电量/延迟/退出），                  |
|               底部 192px 作为虚拟快捷栏（全屏切换/触控手势辅助/虚拟键盘唤醒）。      |
+-----------------------------------------------------------------------------------+
| 方案 B (满屏拉伸 - Stretch to 4:3):                                               |
|   * 画面尺寸: 强行拉伸为 2048 x 1536                                              |
|   * 缺点: 画面纵向拉伸 33.3%，圆形变竖椭圆，文字产生走样，极易引起视觉疲劳。       |
+-----------------------------------------------------------------------------------+
| 方案 C (裁剪填充 - Crop/Zoom to 4:3):                                             |
|   * 缺点: 左右两侧各被切掉约 25% 内容，鸿蒙电脑模式左右两侧的任务栏和时间直接丢失。  |
+-----------------------------------------------------------------------------------+
```

**裁定**：采用 **方案 A（等比 16:9 居中显示，并将黑边转化为控制台）**。

## 5. Wi-Fi Direct 点对点直连端到端延迟预算

由于 Miracast 强制采用 **Wi-Fi Direct (P2P)** 架构，手机作为 Group Owner (GO) 或 Client 与 Nokia N1 建立 1 对 1 点对点 5GHz Wi-Fi 直连，跳过了家用无线路由器中转。

| 阶段 | 流水线阶段 | 耗时区间 (ms) | 典型值 (ms) | 关键优化措施 |
| :---: | :--- | :---: | :---: | :--- |
| **S1** | **手机端屏幕捕获与硬件编码** | 7.0 ~ 11.0 | **8.5** | 鸿蒙麒麟/骁龙硬件 SoC 编码器，极低时延单切片 H.264 模式 |
| **S2** | **Wi-Fi Direct 5GHz 点对点传输** | 1.5 ~ 3.5 | **2.2** | P2P 5GHz 直连信道，无路由器中转竞争，空口延迟极低 |
| **S3** | **TS 解复用与 NAL 组帧** | 0.2 ~ 0.5 | **0.3** | N1 本地轻量级字节扫描，提取 Annex B NALU |
| **S4** | **MediaCodec 驱动与 Intel VED 硬解** | 6.0 ~ 8.5 | **7.0** | Intel 硬件直解 1080p60，非阻塞输入 |
| **S5** | **SurfaceView 硬件叠加层送显** | 4.0 ~ 8.0 | **6.0** | HWC 硬件缩放至 2048x1152，VSYNC 扫描 |
| **总计** | **端到端总延迟 (手机触控 -> 屏幕光子)** | **18.7 ~ 31.5** | **24.0 ms** | **仅延迟约 1.4 帧！达到电竞级交互响应** |

## 6. 关键瓶颈与风险提示（提交讨论）

1. **HDCP 内容保护风险**：
   - 若鸿蒙 4.2 手机在 RTSP M3 `GET_PARAMETER` 中查询 `wfd_content_protection`，Sink 端必须声明 `none`。
   - 需要验证：鸿蒙 4.2 的「电脑模式」在无 HDCP 硬件密钥环境下，是否允许明文桌面传输？（行业经验：桌面与普通办公 App 均允许明文，但 DRM 视频如华为视频 App 会黑屏）。
2. **Android 5.1 Wi-Fi P2P 权限与服务约束**：
   - 传统 Android Wi-Fi Direct 需要弹出系统配对确认弹窗（PIN 码或 PBC 按钮）。如何在 N1 Box 应用内实现静默或一键授权配对，需协议专家深入评估。
